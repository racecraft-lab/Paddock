## User Scenarios & Testing *(mandatory)*

### User Story 1 — WIP Policy Configuration (Priority: P1)

As an operator I configure WIP (work-in-progress) policies per agent, project, workspace, status, branch-pattern, or label-pattern so I can throttle autonomous work without editing scheduler code [Q3, Q4]. Today the scheduler hard-codes `LIMIT 3` and a "3+ in_progress" capacity check; this story replaces those constants with operator-promoted database rows.

**Why this priority**: WIP throttling is the foundational governance capability that retires the hard-coded scheduler constants (the core regression-risk surface). It must ship in MVP before budgets, windows, or override grants because every higher-tier policy depends on the same evaluator and decision-precedence pipeline [Q1].

**Independent Test**: Real Playwright e2e journey under `tests/e2e/governance-wip-policy.e2e.ts` — operator opens the **Cost Tracker → Governance** tab, creates an agent-scoped WIP policy with `limit_value=1`, submits a second autonomous task to that agent, observes the dispatcher emits a `defer` decision with reason `wip_exceeded`, and the diagnostic feed shows the matched policy id. Argos visual snapshots cover empty/populated/loading/error states of the policy editor. Storybook stories cover the WIP indicator panel + policy-row component. Constitution Principle XIV verification: `pnpm test:e2e` + `pnpm test:visual:storybook` both green; `pnpm test:e2e:argos-metadata --mode playwright` confirms snapshot identity tags.

**Acceptance Scenarios**:

1. **Given** `FEATURE_RESOURCE_GOVERNANCE=true` and an active agent-scoped WIP policy with `limit_value=1`, **When** a second task is submitted to that agent while one is `in_progress`, **Then** the dispatcher writes a `defer` decision row, emits an activity entry, and does not advance the second task. [P7-AC3, Q3, Q35]
2. **Given** `FEATURE_RESOURCE_GOVERNANCE=true` and a project/status WIP policy with `limit_value=N`, **When** N tasks are already `in_progress` for that project/status combination, **Then** the next task is deferred with reason `wip_exceeded` until a slot frees. [P7-AC4, Q3]
3. **Given** `FEATURE_RESOURCE_GOVERNANCE=false`, **When** any number of tasks dispatch, **Then** the legacy hard-coded `LIMIT 3` and `3+ in_progress` capacity behavior is preserved byte-for-byte and no governance tables are read. [P7-AC1, AC-FF-Matrix-2, Constitution Principle I]

### User Story 2 — USD/Token/Request/Session Budget Enforcement (Priority: P1)

As an operator I configure budgets in USD, tokens, requests, or sessions with both rolling windows (1h/6h/24h) and calendar windows (daily/weekly/monthly) so I can prevent runaway spend on metered providers and exceed-cap behavior on subscription providers [Q4, Q17]. Each budget has an `enforce_mode` (soft/hard) that decides whether crossing the threshold blocks dispatch or only emits an alert [Q4].

**Why this priority**: Budget enforcement is the second-highest cost-control surface. It must be Priority P1 because subscription accounts (Claude Code Max 20x, ChatGPT Pro, Copilot Pro+) silently degrade or rate-limit when caps are exceeded; without budget governance the operator has no way to detect the slope of spend before the cliff [Q9, Q15].

**Independent Test**: Playwright e2e under `tests/e2e/governance-budget.e2e.ts` — operator creates a daily USD budget with `soft_threshold_pct=80` and `hard_threshold_pct=100`, the synthetic test driver advances the budget ledger past 80% (soft alert fires, work continues), then past 100% (hard block, override grant required). Argos snapshots: budget utilization chart at 0/50/80/95/100%. Storybook: budget chart story renders all six threshold zones. Constitution XIV verification per US1.

**Acceptance Scenarios**:

1. **Given** a daily USD budget with `enforce_mode=soft, soft_threshold_pct=80`, **When** consumption crosses 80%, **Then** an alert/activity row is written and dispatch continues. [P7-AC7, Q4, Q17]
2. **Given** a daily USD budget with `enforce_mode=hard, hard_threshold_pct=100`, **When** consumption reaches 100%, **Then** new dispatch is blocked with reason `budget_exceeded` until an override grant is recorded. [P7-AC8, Q4, Q6]
3. **Given** an OpenAI subscription account (estimated marginal cost = $0), **When** the budget enforces tokens/requests/sessions, **Then** dispatch is still blocked at the configured cap even though USD is zero. [P7-AC9, Q15, Q42]

### User Story 3 — Blackout and Degraded Windows (Priority: P2)

As an operator I configure blackout and degraded windows in my local timezone (default `America/Chicago` / CDT) and mirror provider peak hours (e.g., Anthropic `America/Los_Angeles` / PT) so I align dispatch with cost-aware times [Q2]. Window storage uses IANA timezone identifiers and stores both the rule and the materialized 90-day forward instances to make DST transitions deterministic [Q2, Q46].

**Why this priority**: P2 because windows are predictable schedule shaping rather than emergency stop. They are valuable but the operator can survive without them by deferring tasks manually; budgets and WIP cannot be substituted manually.

**Independent Test**: Playwright e2e under `tests/e2e/governance-windows.e2e.ts` — operator creates a blackout window for "tonight 22:00-06:00 CDT", advances the synthetic clock into the window, observes new autonomous dispatch is blocked while running tasks checkpoint and complete; advances clock past DST spring-forward, confirms the next instance is correctly placed. Argos snapshots: window editor, calendar-mode preview, DST-warning banner. Storybook: window editor stories. Constitution XIV verification per US1.

**Acceptance Scenarios**:

1. **Given** an active blackout window, **When** a new autonomous task or chain advancement is attempted, **Then** it is blocked with reason `blackout_window`; running tasks are allowed to checkpoint and complete. [P7-AC5, Q2]
2. **Given** an active degraded window with allowed-class list `[critical, local, approved-provider]`, **When** dispatch is attempted, **Then** only matching tasks are admitted; all others defer. [P7-AC6, Q2]
3. **Given** a calendar window crossing a DST transition, **When** the materialized 90-day forward instance table is regenerated, **Then** local-time semantics are preserved (no double-fire and no skipped fire). [AC-DST-1, Q46]

### User Story 4 — Override Grants with Atomic Reservations (Priority: P2)

As an operator I grant temporary overrides on blocked decisions with budget reservations that don't permit unbounded spending [Q6, Q42]. Reservations are atomic: under concurrent grant attempts for the same remaining budget, exactly one succeeds with HTTP 201 and all others receive deterministic 409 [AC-Race-1, Q6, Q40].

**Why this priority**: P2 because overrides only make sense once US2 (budgets) is enforcing. The race-free reservation requirement is a NON-NEGOTIABLE correctness property — the system must never permit two concurrent grants to both reserve the same dollar.

**Independent Test**: Playwright e2e under `tests/e2e/governance-override-grant.e2e.ts` — happy-path: operator grants a $5/2-hour override for a `defer:budget_exceeded` decision; conflict-path: synthetic load fires 5 concurrent grant POSTs for the last $1 of budget, exactly one returns 201 and four return 409 with deterministic error body [Q6, Q41]; precondition-failure path: concurrent edits to the policy return 423 (locked) and stale ETag returns 412 (precondition failed) [Q41]. Argos snapshots: override grant form, 409/422/423/412 error toasts. Storybook: override grant form stories with all error states.

**Acceptance Scenarios**:

1. **Given** a `defer` decision with reason `budget_exceeded` and remaining budget $5, **When** the operator submits a $5/2-hour grant, **Then** the system creates a reservation row, links the override grant to the original decision, and emits an audit row. [P7-AC8 supplement, Q6, Q66]
2. **Given** 5 concurrent grant POSTs each requesting the last $1, **When** the requests reach the reservation hot path, **Then** exactly one returns 201 and the other four return 409 with body `{"error":"reservation_unavailable","reason":"budget_concurrent","remaining_usd":0}`. [AC-Race-1, Q6, Q40, Q41]
3. **Given** an idle reservation older than its TTL, **When** the reservation reaper runs, **Then** the row is released, an audit-log entry is written, and the reaper alert fires if the count exceeds the soft threshold. [Q66]

### User Story 6 — Diagnostic "Why Was This Blocked?" View (Priority: P2)

As an operator I see WHY a specific dispatch was deferred or blocked via the diagnostic view [Q44, Q54]. Each `decision` row carries the matched policy ids, the precedence ordering applied, the budget snapshot at evaluation time, the breaker state, and a deep-link to the audit chain [Q1, Q35, Q44].

**Why this priority**: P2 — the diagnostic view is the operator's debugging tool when a task does not advance and converts an "unexplained block" into an actionable next step. Independent of US5's at-a-glance summary view.

**Independent Test**: Playwright e2e under `tests/e2e/governance-diagnostic-feed.e2e.ts` — operator filters the diagnostic feed by `agent=Aegis` + `reason=budget_exceeded`, paginates 100+ entries, expands one entry to see the full evaluation trace, follows the audit deep-link. Argos snapshots: feed empty/populated/dense/expanded states. Storybook: diagnostic-feed-row component stories.

**Acceptance Scenarios**:

1. **Given** an autonomous dispatch was deferred due to a WIP policy, **When** the operator opens the diagnostic feed, **Then** the entry shows the matched `policy_id`, `precedence_rank`, evaluator latency in ms, and the snapshot of in-progress task counts at evaluation time. [Q44, Q1, Q35]
2. **Given** an autonomous dispatch was blocked due to a hard budget, **When** the operator expands the entry, **Then** the budget ledger snapshot, override-grant suggestions, and the breaker state are visible. [Q44, Q17, Q21]
3. **Given** the operator filters by `reason=evaluator_error`, **When** the entry expands, **Then** the fail-safe path is documented (defer + audit + activity + notification + circuit-breaker tick) and the runbook link is rendered. [P7-AC12, Q44, Q61]

### User Story 7 — Multi-Source Defense-in-Depth Telemetry (Priority: P2)

As an operator I rely on multi-source defense-in-depth telemetry ingestion so my budgets remain correct even when a single source is degraded [Q16, Q18, Q19, Q23]. The system ingests from Claude Code OTel, Codex CLI stdout+rollout, Copilot CLI events.jsonl, Ollama logs, LM Studio logs, and the OpenClaw gateway in parallel, reconciling raw events into a canonical event ledger via a deterministic dedupe-and-coalesce reconciler [Q24, Q26, Q39, Q52].

**Why this priority**: P2 because the multi-source story is what makes US2 (budgets) trustworthy. Without it, a single CLI degradation makes budget counters silently drift. Independent of US1 (WIP only depends on Mission Control's own task table).

**Independent Test**: Playwright e2e under `tests/e2e/governance-telemetry-health.e2e.ts` — operator opens System Health dashboard, sees per-source health pills (green/amber/red), clicks a red pill to drill into staleness/lag/admission-rejected counts, observes the breaker-open banner when admission control trips. Argos snapshots: every health-pill state, breaker-open banner, drilldown panel. Storybook: source health pill, breaker banner, drilldown stories.

**Acceptance Scenarios**:

1. **Given** Claude Code OTel emits a usage event AND the OpenClaw gateway emits the same usage event for the same `provider_request_id`, **When** the reconciler runs, **Then** exactly one canonical event is materialized with provenance set to `merged` and the duplicate-dedupe counter increments. [Q18, Q24, Q26]
2. **Given** Codex CLI stdout `turn.completed.usage` and the rollout file emit identical `provider_timestamp_ms` for the same turn, **When** the join precondition is verified, **Then** the canonical event is materialized once with `join_confidence=high`; if timestamps disagree, the join is downgraded and a drift alert is recorded. [Q39, Q52]
3. **Given** the OTLP receiver experiences a sustained ingestion burst above the admission-control ceiling, **When** raw ingestion saturates, **Then** the emergency circuit trips, surplus events are shed with a counter, and operator-visible self-observability metrics fire an alert. [Q47]

### Edge Cases

- **Concurrent operator edits to the same policy**: Detected via ETag/If-Match precondition; second writer receives HTTP 412 (precondition failed) or 423 (locked); UI surfaces the conflict and offers a refresh-and-retry affordance. [Q41, Q46]
- **DST spring-forward / fall-back transitions**: Calendar windows preserve local-time semantics; the materialized 90-day forward instance table is regenerated such that no instance is double-fired and none is skipped. [Q46, Q2]
- **Counter↔ledger drift detected via stratified sampling**: Drift > tolerance triggers an auto-repair attempt for low-magnitude drift and operator-confirmed repair for high-magnitude drift. [AC-Drift-1..4, Q40, Q58]
- **Aegis governance starvation**: If Aegis would be starved by the policy stack (e.g., budgets + WIP + windows all blocking), an emergency-reserve allocation kicks in to keep the review pipeline alive; soft alert escalates per a documented runbook. [AC-Aegis-1..6, Q5, Q20, Q42, Q53]
- **OpenAI subscription account at $0 estimated marginal cost**: Token/request/session budgets still enforce; the evaluator does NOT short-circuit on USD-only checks. [P7-AC9, Q15, Q42]
- **Multi-region or multi-node deployment**: Out of scope; v1 assumes single-process Node.js + better-sqlite3 single node.
- **Retroactive task cancellation when budget exceeds mid-execution**: Out of scope; v1 only blocks new dispatch and chain advancement, not running work.
- **30-minute soak at 100 admission/sec + reconciler load**: p95 stays < 15 ms; memory growth < 50 MB. [AC-Soak-1, Q46, Q55]
- **Reservation reaper backlog**: When idle reservations exceed soft threshold, the reaper emits a breaker-restart-count alert and a reservation-reaper alert. [Q66]
- **Aegis emergency-reserve badge visibility**: When emergency reserve is engaged, a badge renders on the Aegis row in the Governance tab; the badge has Storybook stories for default / engaged / cooling-down states. [Q53, FR-306..315]
- **Hard-enforcement disablement**: If an operator attempts to globally disable hard enforcement (e.g., flips a kill-switch), a 4-step escalation flow with a typed-confirmation gate is required and audited. [Q59]

## Requirements *(mandatory)*

All FRs MUST be testable. Each FR cites the design-concept Q-section(s) it derives from via `[Q<n>]` markers. Every UI-touching FR cites Constitution Principle XIV (Playwright + Storybook + Argos). Every flag-gated FR cites Constitution Principle V (`resolveFlag`).

### FR-001..030: Evaluator + Decision Precedence + Scheduler Gates [Q1, Q5, Q11, Q13, Q21, Q35, Q59]

- **FR-001**: System MUST provide a `resourcePolicyEvaluator(decisionInput)` function that returns one of `{allow, defer, block}` plus a `reasons[]` array, deterministic for a given input snapshot. [Q1, Q11]
- **FR-002**: Evaluator MUST apply a documented decision precedence: (1) hard breaker open → defer; (2) blackout window match → block; (3) hard budget exceeded → block; (4) WIP exceeded → defer; (5) degraded window with non-allowed class → defer; (6) soft budget threshold → allow + alert; (7) all clear → allow. [Q1]
- **FR-003**: Evaluator MUST be invoked at four scheduler gate points: (a) initial task admission, (b) chain advancement, (c) periodic re-eval for in-flight long-running work checkpoints, (d) override-grant validation. [Q1, Q35]
- **FR-004**: Evaluator MUST be a hot-path function meeting `p50<5ms, p95<15ms, p99<25ms` admission latency on Ryzen 5900XT + 64GB RAM with 1k policies + 300k ledger rows + concurrent gates active. [AC-Bench-1, Q11, Q35]
- **FR-005**: Evaluator MUST fail safe on internal exception: write a `defer` decision, an audit row, an activity row, fire a notification, and tick the circuit breaker. [P7-AC12, Q21]
- **FR-005a**: The FR-005 defer decision row, audit row, and activity row MUST be written within a single `db.transaction(() => { ... })`; the notification (severity=`high`, channel=`activity_feed` + `system_health_dashboard`, audience=`operator`) and circuit-breaker tick MUST fire on transaction commit via a post-commit hook. On post-commit hook failure (e.g., notification dispatch error) the evaluator MUST emit a self-observability counter `evaluator_postcommit_dispatch_error` and retry the dispatch on the background connection up to 3 times; the durable defer/audit/activity rows are not rolled back. The defer reason code MUST be `defer:evaluator_internal_exception` to distinguish from `defer:retry_exhausted` (FR-012) and `defer:invalid_policy` (FR-026). [P7-AC12, Q21, Q44]
- **FR-006**: Circuit breaker state MUST be persisted to the database (not in-process) so that breaker open/half-open/closed survives process restart and is deterministic across replicas. [Q13, Q21]
- **FR-007**: Circuit breaker MUST support a deterministic mode for tests where state transitions are driven by an injectable clock and counter. [Q13, Q21]
- **FR-008**: Evaluator MUST be gated by `FEATURE_RESOURCE_GOVERNANCE` resolved via `resolveFlag(name, ctx)` against the requesting task's workspace; flag OFF preserves byte-compatible legacy `LIMIT 3` + "3+ in_progress" behavior. [P7-AC1, AC-FF-Matrix-2, Constitution Principle I, Constitution Principle V]
- **FR-009**: Decision rows MUST include `decision_id` (uuid), `task_id`, `agent_id`, `workspace_id`, `evaluator_version`, `policy_ids[]` matched, `precedence_rank`, `reasons[]`, `latency_ms`, `breaker_state`, and `evaluation_snapshot_json`. [Q1, Q44]
- **FR-010**: Decision rows MUST be append-only with no UPDATE permitted; corrections are coalesced into a separate correction ledger. [Q26, Q30]
- **FR-011**: Evaluator MUST support background-workload priority: long-running maintenance jobs (counter rebuild, reconciler) MUST NOT block hot-path admission; the foreground/background DB connection separation enforces this. [Q29, Q35]
- **FR-012**: Atomic counter conditional update MUST use a `WHERE counter_value = expected_old_value` clause; on rowcount=0 the evaluator retries up to 3 times with exponential backoff; persistent retry-exhaustion writes a `defer:retry_exhausted` decision. [Q35, Q40, Q50]
- **FR-013**: Aegis tasks MUST be subject to evaluator governance with starvation-prevention provisos applied per FR-151..170. [Q5, Q42]
- **FR-014**: Hard budget thresholds MUST require operator override grants per US4 to permit additional dispatch; the override grant MUST link to the originating decision row. [P7-AC8, Q6, Q66]
- **FR-015**: Soft budget thresholds MUST emit an alert + activity row but allow dispatch. [P7-AC7, Q4]
- **FR-016**: Evaluator MUST log a structured event for every decision; evaluator latency histogram is a self-observability metric. [Q44, Q45]
- **FR-017**: Evaluator MUST respect `enforce_mode` per policy (`soft`, `hard`, `dry_run`). [Q4]
- **FR-018**: Evaluator dry_run mode MUST shadow-write decisions to a `dry_run_decisions` view without affecting live admission. [Q4, Q14]
- **FR-019**: Evaluator MUST resolve all flag checks through `resolveFlag` — inline `process.env.FEATURE_*` is forbidden. [Constitution Principle V]
- **FR-020**: Evaluator MUST be deterministic given identical inputs and clock; reproducibility test suite asserts this. [Q14]
- **FR-021**: Hard-enforcement global disable MUST require a 4-step typed-confirmation escalation flow logged to the audit chain; the escalation surfaces in the activity feed and Workspace Governance Health dashboard. [Q59]
- **FR-022**: Persistent breaker open beyond `breaker_open_max_seconds` MUST emit a high-priority alert and surface a runbook link. [Q21, Q66]
- **FR-023**: Evaluator MUST NOT consult external services (gateway, OTLP receiver) on the hot path; only the local SQLite database. [Q11, Q47]
- **FR-024**: Evaluator MUST emit a self-observability counter for each precedence-rank outcome (admit / defer / block) bucketed per minute. [Q45]
- **FR-025**: Evaluator state inputs (current WIP counts, budget counters, breaker state, window state) MUST be read consistently within a single SQLite read transaction to avoid torn reads. [Q35]
- **FR-026**: Evaluator MUST reject unknown `enforce_mode` values with a typed validation error and write a `defer:invalid_policy` decision. [Q41]
- **FR-027**: Evaluator MUST respect a per-policy `enabled_at` / `disabled_at` window so policies can be staged without going live. [Q12, Q56]

- **raw_usage_event**: Append-only per-source event with provenance.
- **canonical_usage_event**: Deduped + reconciled event, posted to budget ledger.

- **reconciliation_batch**: Tracking row for incremental reconciler progress.
- **source_emission_capability**: Per-source registry of units / fields / cadence.
- **audit_log_entry**: Tamper-evident chain row with prev_hash → curr_hash linkage.
- **circuit_breaker_state**: Persistent breaker state per scope (closed/half-open/open) + counters.
- **retention_policy**: Per-table retention horizon configuration.
