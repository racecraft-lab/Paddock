# Contract: Seed Evidence

SPEC-009B evidence is durable JSON or Markdown generated by the seed command and referenced from the operator runbook. It must distinguish seed readiness, blocked cleanup preflight, successful seed application, idempotent rerun, and non-dispatch verification.

## Evidence Sections

| Section | Required | Description |
|---------|----------|-------------|
| `preflight` | Yes | Clean or blocked residue result before mutation. |
| `seed_shape` | Yes for apply/verify | Product Line, Facility, departments, assignments, repo, workflow, flags, and governance identities. |
| `idempotency` | Yes for verify | Before/after counts from two seed runs. |
| `non_dispatch` | Yes | Counts and static checks proving forbidden pilot/run/sandbox state is absent. |
| `redaction` | Yes | Proof that raw credential-like values were not emitted. |
| `operator_cleanup` | Yes | Checklist path and cleanup status for non-Mission-Control/FocusEngine residue. |

## Validation Rules

- `preflight.mutation_status` is `not_mutated` for preflight mode and blocked results.
- Blocked evidence includes residue summaries and snapshot hashes proving unchanged non-Mission-Control residue.
- Successful apply evidence includes workflow-contract `run_id` and `contract_hash`.
- Idempotency evidence compares stable identity counts, not generated timestamps.
- Non-dispatch evidence must fail if any SPEC-009B-owned code creates a new task, successor, runner, sandbox, synthetic issue, claim, dispatch, auto-merge, or reconciliation side effect.
- Evidence never includes raw credential-like values.
